# callis-js: Implementation Plan (TypeScript + Bun native binary)

Plan v3.6, 13 October 2026. A port of the JVM `reachability-analyzer` to the npm ecosystem, branded **callis** (project `callis-js`), shipped as a single native binary built with `bun build --compile`.

- Measured facts replace estimates: npm OSV snapshot is **208 MB / 230,324 records** (not "far larger"); Bun 1.4.2 compile experiments settled §7 (autoload flags, worker rule, 7+1 targets, ~81 MB, ~4 ms).

**v3.2 → v3.3 (third external review, 13 October 2026 — all P0s, C1–C8, and the three design decisions verified accurate against the v3.2 text; the P1s applied with the noted adjustments):**
- **Soundness contract (P0.1):** §5.5 classifies every supported construct as *modeled / conservatively approximated / unsupported*; unresolved behavior is explicit in the IR and propagates into `confidence` and `exposure`; new `exposure.dynamicUnscoped` (markers not attributable to any package); machine-readable `limitations` in the report; the 80% oracle floor is explicitly an **acceptance gate, not evidence of safety**; release criterion: *no claim of complete reachability*.
- **Import-time execution (P0.2):** per-module `module-init` graph node (§5.4) — `import "pkg"` is a graph edge and top-level side effects are in the graph; a mapping target executed at import time is REACHABLE at mapping level (`import → module-init → target`) even when the artifact is below the evidence tier; `evidence.callbackRegistered` is its own field (registration ≠ invocation; `callbackInvoked` tracking is a documented post-v1 limitation).
- **Advisory normalization (P0.3):** records normalize into per-package internal records; dedup merges only on **verified identity + compatible ranges** (union of ranges and source record ids) — never on alias-set overlap; the canonical id is a presentation field, not a dedup key; entries with no determinable package identity **do not match** (the ecosystem-fallback match is removed; the ecosystem only filters which records are read).
- **Install reconciliation (P0.4):** per-component resolution states `RESOLVED | MISSING | VERSION_MISMATCH | AMBIGUOUS` in the report; `--strict-sources` now fails on *any* non-`RESOLVED` component (v3.3 — previously only missing); a deterministic **install fingerprint** (instance identities + realpaths + install-state file) joins the cache keys, and loaded-file content hashes catch in-place patches.
- **Resolution profiles (P0.5):** three explicit profiles — runtime resolution (Node semantics, **no `tsconfig` `paths` at runtime**: a TS alias that does not runtime-resolve must not invent a production edge), TS source mapping (locations only), bundler adapters (post-v1); every decision recorded; unresolved modules stay unresolved; M2 fixtures pinned against actual supported-Node resolution behavior.
- **Native opacity (P0.6):** the boundary is a graph node (package, exported symbol, incoming call sites) with `nativeBoundary: reached | unresolved`; new `--opaque-native=fail|warn|ignore` (default `warn`); *engine opacity ≠ component unreachability*.
- **Cache: three tiers (P0.7):** per-file IR key / call-graph key / final-report key (what `--print-cache-key` prints); the install fingerprint; full-result caching disabled when installation integrity cannot be established; the real cache read/write consumes the same canonical definition (M8 invalidation matrix).
- **Completeness independent of policy (P0.8):** mandatory `analysisStatus: COMPLETE | PARTIAL | INCOMPLETE | NOT_PERFORMED` + `completeness` block (component states, unresolved imports, unscoped markers, opaque boundaries, graph state) in every report; the exit code is a policy decision over findings *and* completeness — a green run with `PARTIAL` says so.
- **Verdict epistemics + the clean-result principle (P1.1):** `UNREACHABLE` (label kept for JVM parity) is *no path found within the modeled subset*, not proof of absence; the principle — *a clean result means no policy-triggering finding was established, and must not be presented as proof that every vulnerability is unreachable* — now governs verdicts, dynamic-risk reporting, source-resolution policy, exit codes, and docs.
- **`--sbom-only` contract (P1.3):** `analysisStatus: "NOT_PERFORMED"`, no `REACHABLE`/`UNREACHABLE` verdicts, SARIF/JUnit must not misrepresent the result as a successful reachability check.
- **P1s applied:** DEV_ONLY means *excluded from analysis, not safe* (build-tool fixtures); stable identity for malware findings (`warn|ignore` changes the exit code, never suppresses the finding; a malformed `MAL-*` record is never downgraded); determinism normalization contract (P1.7); npm platform-selection matrix + shim diagnostics + install-matrix test (P1.8); worker hardening limits (P1.5); the parser fast path is gated on differential-IR equivalence (P1.4).
- **M6/M7 boundary (C1–C3):** v1 = standalone release binary + `callis-check.yml` + Jenkinsfile; the npm packages, the GitHub Action, and the build-tool cache integration ship post-v1 (M7).
- **Compatibility matrix (C6)** added to §1; the **supported-framework matrix freezes in M0** with ≥1 positive + ≥1 negative entry-point fixture per framework (C7); the **runtime-adapter contract (C8)** — identical core fixtures under Bun and Node.
- **Early design decisions (5.1–5.3):** threat model (trusted vs untrusted inputs, per-class controls; a checksum computed from the same untrusted artifact is not independent evidence), engine/policy separation (`AnalysisResult` + a separately tested policy layer), `schemaVersion` (independent of `toolVersion`; SARIF pinned to 2.1.0).
- **§9 gained:** the 14 boundary tests + a metamorphic suite (behavior-preserving transforms must not remove known paths), the resolver fixture expansion (P0.5), the cache invalidation matrix, the normalization contract.
- **Timeline (review §8):** the 20–28-week range holds with the upper end as a baseline, not a ceiling; a **midpoint scope-reduction trigger in M4** (shrink the framework set or defer precision features rather than compressing validation). New risks R12 (install drift) and R13 (stale caches).

**v3.3 → v3.4 (fourth external review, 13 October 2026 — all 14 points verified accurate against the v3.3 text; the three blocking items change v1 scope):**
- **`tsconfig` aliases for Next/Nest (1, blocking):** the v3.3 "no `paths` at runtime" rule broke the v1 frameworks that depend on them (Next resolves `@/…` through its own compiler, Nest through its build). v3.4: for **application code only**, `paths`/`baseUrl` apply when the project shows a runtime-resolution mechanism (Next config, Nest build, `tsconfig-paths`, `tsc-alias`, `module-alias`); those edges are marked `resolution: "tsconfig-alias"` with degraded confidence; an alias with no mechanism stays unresolved (the v3.3 negative fixture holds); M0 decides — apply, or drop Next/Nest from the v1 matrix.
- **Pre-run cache key (2, blocking):** `--print-cache-key` now prints the **input key**, computable *before* the run (versions, SBOM, OSV pin, mappings, every lockfile variant, install fingerprint, **whole-tree application-source hash** with the exclusion list, flags) — the Turborepo/Nx task hash. The **memo key** (entry-point set, resolved graph, loaded-file IR keys, model/resolver versions) is internal, recorded in the report (`keys.memo`), and consumed by callis's own memoization. New `--hash-installed` (content-hashes installed files into the input key; without it, task-level caching cannot see an in-place patch — documented).
- **v1 ships a verifiable, downloadable binary (3, blocking):** M6 now includes GitHub Release assets + `SHA256SUMS` + cosign + provenance (cheap in CI — the threat model's "signed release artifacts" are actually true in v1) and the multi-arch Docker image (`docker buildx`); **v1 (M6) is explicit for both**; `callis-check.yml` downloads the pinned binary from the release and verifies SHA256 + cosign before running. M7d keeps only the npm packages + macOS notarization + Windows Authenticode.
- **Timeline re-estimated (4):** the v3.3 "range holds" claim was wrong — the arithmetic was 17–22 (not 17–22.5) → 20–27, not 20–28, and v3.3's additions to M0/M2/M5/M6/M8 went unpriced. New per-milestone estimates: M0 3–4, M2 2.5, M5 3, M6 2.5, M8 1.5 → M0–M6 = **20.5–25.5**; + 3–5 buffer → **v1 ~24–31 weeks** (best case 20.5; the original 13–16 is historical, pre-measurement). The M4 trigger now has a **measurable criterion** (weeks 3–4: package-boundary recall below the ratified minimum on 2 of 3 apps, or micro-corpus pass below 95% → shrink the framework set or defer precision).
- **`analysisStatus` made usable (5):** `COMPLETE` = every component `RESOLVED` + graph built + no unresolved imports; **dynamic markers never demote the status** (they live in `exposure`/`limitations` — nearly every real project has some, so the old definition made `PARTIAL` the norm and the status noise); new `--require-complete` (exit 3 on `PARTIAL`) for strict CI.
- **`AMBIGUOUS` no longer contradicts "separate instances" (6):** multiple instances of one name+version (hoisting, pnpm peer-dependency variants) are the **normal case — separate instances, each with its own verdict, never tripping `--strict-sources`**; `AMBIGUOUS` only when one SBOM component cannot be tied to any instance through the SBOM `dependencies[]` graph.
- **`VERSION_MISMATCH` matches the right version (7):** the advisory range is evaluated against the **installed** version (what actually runs), not the SBOM version; the finding carries both `componentVersion` and `installedVersion`; an installed version outside the affected range is reported as such.
- **Merge rule defined (8):** "compatible ranges" = **equal after normalization** → merge (union of source ids/aliases); otherwise **separate findings linked by `relatedIds`** and grouped in the report.
- **`--sbom-only` consistent (9):** `resolutionState: NOT_CHECKED` (no filesystem in this mode — `NO_SOURCE` is dropped, not misused); new **`--fail-on-applicable`** (any applicable non-malicious advisory ⇒ exit 1); **without it, only `MAL-*` affects the exit code** — a plain-vulnerability gate is reported but not silently green, and the report says exactly what was checked.
- **Evidence fields unambiguous (10):** `called` = direct call or `new` **only**; `callbackRegistered` = package function passed as a value; the `call` tier is met by either by default — new **`--call-evidence=direct`** requires direct calls only.
- **Verdict precedence (11):** `REACHABLE` wins whenever the evidence tier is met (a call into a covered addon's JS wrapper ⇒ `REACHABLE`, exit 1 by default); `NATIVE_OPAQUE` applies only when the path ends at a boundary beyond which the vulnerable code cannot be seen **and the tier is not otherwise met** (the boundary is the only evidence).
- **Empty-SBOM guard (12):** zero analyzable npm components ⇒ **exit 3** (a run that analyzes nothing is a broken input, never a clean one); explicit opt-out `--allow-empty-sbom`.
- **`exposure.loadedNotCalled` (13):** the count of packages LOADED but below the configured evidence tier — import-time exposure that unmapped advisories cannot see, visible without opening findings.
- **Dangling references and stale text (14):** the **boundary-test table added to §9** (M5 cited it; §9 had none); §12 heading → v3.4; ADR references now prefixed `JVM` / `callis` (no more number collisions — callis ADR 0011 is the soundness contract, JVM ADR 0011 the diagnostic sink); the threat model says the OSV **source is trusted for authenticity, the record contents are still parsed as untrusted data**; the metamorphic suite now has milestone owners (**M4–M5**).

**v3.4 → v3.5 (fifth external review, 13 October 2026 — all nine points verified accurate against the v3.4 text; item 1 is a false-negative path and item 4 changes v1 platform scope):**
- **Installed-but-unlisted packages (1, high):** candidates come from SBOM × OSV and reconciliation ran SBOM→disk only, so a package the graph loaded but the SBOM omitted (stale lockfile, different tree) was never checked and the run could exit 0 `COMPLETE`. v3.5: the graph's loaded instances are checked back against the SBOM — an unlisted instance goes into `completeness.unlistedInstalled`, demotes the status to `PARTIAL`, and gets a NOTICE; new **`--match-installed`** also generates candidates from the installed instances; golden demo; new risk R14.
- **`PARTIAL` still noisy (2, high):** v3.4 demoted the status for any recorded unresolved import, but those are ubiquitous — optional `try { require("bufferutil") }` imports, peer dependencies, platform-specific modules, `node:` builtins. v3.5: builtins are resolved (`builtin` classification, never unresolved); only an unresolved import **in application code, or in a package that carries a candidate advisory** counts toward `PARTIAL`; everything else stays in `completeness.unresolvedImports` + `limitations`; the `ws`-without-`bufferutil` demo stays `COMPLETE`.
- **The M4 trigger compared mid-milestone progress to the final target (3, high):** at weeks 3–4 of a 6–10-week milestone the graph is still under construction, so package-boundary recall was below the 80% ratified minimum almost by definition — the trigger fired regardless. v3.5: a **ramp** — ≥50% at weeks 3–4, ≥70% at week 6, the ratified 80% only at exit; the micro-corpus ≥95% threshold stays; the ramp is ratified in M0 together with the minimum.
- **Release verification was not independent, and v1 platform support was unclear (4, high):** the template verified SHA256 + cosign against the release's own `SHA256SUMS` (a checksum from the same source is not independent evidence — §3.16), and v1 built all seven targets without declaring which are supported (notarization/Authenticode deferred to M7d; M2's fixture matrix ran on POSIX CI only). v3.5: the template **pins the expected digest in the repo (Renovate updates it with the version bump) and runs `cosign verify` against the documented certificate identity + OIDC issuer** (cosign installed by the template); **Linux (glibc and musl, x64 and arm64, plus the baseline build) is the supported v1 platform — the macOS/Windows binaries ship as experimental and unsigned** (smoke-tested; M7d signs them); M2's fixture matrix also runs on a Windows runner.
- **The input-key exclusion list could hide analyzed files (5, medium):** `dist/`, `build/`, `.next/` were excluded from the whole-tree source hash, but a Nest or Next app may have `main` pointing into `dist/` — analyzed application code whose edits would not change the key. v3.5: the exclusion list is the default; **any directory that contains a resolved entry point or a loaded application file is auto-included, with a warning**; `--source-exclude`/`--source-include` override; fixture.
- **The empty-SBOM guard fired on all-dev SBOMs (6, medium):** v3.5: "empty" = **zero npm components before dev filtering** — an all-dev SBOM exits 0 with the `DEV_ONLY` verdicts listed and an explicit NOTICE (use `--include-dev`), not exit 3; the guard applies under `--sbom-only` too; **`--fail-on-applicable` without `--sbom-only` is a usage error (exit 2)**.
- **`AMBIGUOUS` needed an SBOM dependency graph (7, medium):** many SBOMs (SPDX 2.x in particular) have no `dependencies[]` — the rule then marked every duplicated package `AMBIGUOUS`, tripping `--strict-sources`. v3.5: the component→instance tie falls back to **the lockfile's resolved graph**; if that is also unavailable, duplicate instances stay **separate instances, never `AMBIGUOUS`**, and `completeness.dependencyGraph: "absent"` records the gap.
- **Pipeline order was circular for `VERSION_MISMATCH` (8, medium):** candidates were generated from SBOM × OSV (version-filtered on the SBOM version) before resolution, and the matcher's "use the installed version" rule had no stated order — the stale-SBOM case (SBOM version outside every affected range, installed version inside) produced no candidate at all. v3.5: the order is stated explicitly — **resolve components first, then generate and match**; a mismatched component is evaluated against **both** versions and a finding is kept if either is in range, labelled `matchedOn: installed | sbom | both`.
- **Housekeeping:** §2's Distribution row still budgeted signing in M7d (release assets + cosign + provenance are M6; macOS/Windows signatures stay M7d); R13 "three-tier (IR / call-graph / report)" (now IR / input / memo); R1 listed three `exposure` fields (there are five); R12 omitted `NOT_CHECKED`; §3.8 named the GitHub Action without a post-v1 marker; the §9 markdown breakage fixed (an unmatched `**` in the resolver bullet — the v3.4 alias-pair sentence swallowed the rest of the bold chain — and the boundary-test table moved out of the bullet list, with six v3.5 rows added); the timeline now states the exact sum (**23.5–30.5 weeks, ~24–31**); the report carries **`exitReasons[]`** — every triggered condition, independent of the precedence winner — so CI that routes exit 1 and exit 3 to different queues reads the list, not the exit code (documented in the README).

**v3.5 → v3.6 (structure, 13 October 2026):** **ADRs 0001–0017 written as separate documents under `docs/adr/`** (sibling convention from `dependency-vulnerability-analyzer`: 0001 = bootstrap record + index, 0002–0017 one per §3 decision; **future changes amend the specific decision ADR in place**). The plan body is unchanged; each ADR cites its plan section as the source of record and carries the refinements accumulated through v3.1–v3.5 (b2 alias profile, the input/memo key split, the tie-graph fallback, `exitReasons[]`, the platform-support declaration, …). ## 1. Goal and scope

Answer the same CI question for JavaScript and TypeScript projects: **is this vulnerability in the SBOM actually reachable from application code?**

Pipeline: `CycloneDX / SPDX 2.x SBOM` + `local OSV npm database` → candidate vulnerabilities → `JS/TS call graph` (entry points → app source + resolved `node_modules`) → `REACHABLE / UNREACHABLE` verdicts with call traces → JSON + JUnit XML + SARIF.

**Preserved contract (flag-compatible with the existing CI templates — a mechanical rename, not drop-in):** the flag vocabulary below is identical, but the binary is now `callis`, the default report base `callis-report`, the report `tool.name` "callis", the cache dir `$XDG_CACHE_HOME/callis`, and the template `callis-check.yml`. Any existing template that invokes the JVM binary, globs `reachability-report.*`, or a downstream SARIF consumer that filters on `tool.name`, needs a one-line rename.

**Compatibility matrix (v3.3, C6):** every deliberate deviation is labeled here, not discovered downstream:

| Contract | callis behavior | Deviation? |
| --- | --- | --- |
| Binary / report base / `tool.name` / cache dir / template | `callis` / `callis-report` / "callis" / `$XDG_CACHE_HOME/callis` / `callis-check.yml` | Renamed — one-line template change |
| `--app-classes` + `--classpath-file` | collapsed into `--project` | Merged |
| `--java-version` | dropped | Removed |
| Exit codes `0/1/2/3` | identical semantics, plus **two JS-specific exit-3 conditions** (the total-resolution guard and the empty-SBOM guard, §5.3; v3.4) | Additive |
| New flags | `--sbom-only`, `--strict-sources`, `--include-dev`, `--include-tests`, `--malware`, `--package-evidence`, `--call-evidence`, `--over-approximate-dynamic`, `--opaque-native`, `--print-cache-key`, `--hash-installed`, `--require-complete`, `--fail-on-applicable`, `--allow-empty-sbom`, `--match-installed`, `--source-exclude`, `--source-include` | JS-only additions (JVM consumers ignore them) |
| Verdicts | `REACHABLE`, `UNREACHABLE` kept; added `NO_SOURCE`, `DEV_ONLY`, `MALICIOUS_PACKAGE`, `NATIVE_OPAQUE` | JS-only additions; `UNREACHABLE` keeps the JVM name with the v3.3 epistemics (§5.6): *no path found within the modeled subset*, not proof of absence |
| Report fields | JVM parity fields + `exposure`, `analysisStatus`, `completeness`, `limitations`, `schemaVersion`, `supplyPath`, `matchLevel`, `confidence`, `nativeBoundary` | Additive; `schemaVersion` is independent of `toolVersion` |

- Exit codes: `0` clean, `1` any REACHABLE, `2` usage/config error, `3` analysis failure. A run that ends before reporting deletes stale reports under `--output` **at the start of the run, for exactly the formats selected** (JVM `AnalyzerEngine` parity).
- Same flag vocabulary where it makes sense: `--sbom`, `--osv-dir`, `--osv-checksum`, `--mappings`, `--entry-points`, `--callback-interfaces`, `--cha`, `--pointer-analysis`, `--format`, `--output`, `-v` — names kept exactly from the JVM CLI (verified flag-for-flag), so existing CI templates port with minimal diff. `--app-classes`/`--classpath-file` collapse into `--project`; `--java-version` has no JS counterpart and is dropped.
- Same report trio (`<base>.json`, `<base>.junit.xml`, `<base>.sarif`), default `--format=json,junitxml` (SARIF opt-in, as in the JVM tool; the CI template passes all three).
- Same "fail visibly, never silently green" philosophy: the JVM exit-3 list is ported in full — zero-valid-records OSV directory, zero detected entry points, call-graph build failure/OOM, **report destination not writable** — plus the JS-specific **total-resolution guard** (every analyzable component non-`RESOLVED` ⇒ exit 3, §5.3) and the **empty-SBOM guard** (zero npm components before dev filtering ⇒ exit 3, v3.4; refined v3.5 item 6; `--allow-empty-sbom` opt-out) — neither is in the JVM list. **Exit-code precedence (v3.2): `2 > 3 > 1 > 0`** — usage/config errors first, then analysis failures (guard, `--strict-sources`, OOM), then reachable findings; a run exits 3 even when reachable findings also exist (§6).
- Local OSV snapshot with sha256 pinning. SPDX 3.x refused explicitly (exit 2).
- **License (v2, timing fixed in v3.1):** MIT — declared at the **M0 bootstrap** (LICENSE file + `license` field in every workspace `package.json` from the first commit; every npm package needs the field before its first publish). The JVM repo has no license; npm publishing requires one.

**Out of scope for v1:** taint/data-flow analysis (a reachable function is not proof of exploitability), analysis of already-bundled output (webpack/esbuild bundles; analyze sources), browser-only code paths (opt-in later), Deno, Yarn PnP (refused, exit 2, hint to `nodeLinker: node-modules`), and non-npm ecosystems (PyPI etc. are a later porting exercise on the same engine).

## 2. What carries over and what changes

| Concern | JVM tool | JS tool |
| --- | --- | --- |
| Call-graph engine | SootUp (mature, off the shelf) | **Must be built**: no SootUp equivalent exists for JS. This is the main cost and risk. |
| Dispatch model | RTA / CHA / SPARK | Field-based flow-insensitive analysis, demand-driven from entry points. Flags `--cha` and `--pointer-analysis` map to the less and more precise variants (§5.5). |
| Component → code mapping | Maven GAV → jar on classpath | purl → installed directory in `node_modules` (npm, pnpm, Yarn, Bun layouts) |
| Static-analysis difficulty | Typed, closed-world bytecode | Dynamic: `require(expr)`, computed property calls, prototype mutation, `eval`, monkey-patching |
| OSV data | `Maven/all.zip`, ~7k records, 10.3 MB, no symbols | `npm/all.zip`, **measured 2026-10-13: 218,363,616 bytes compressed, 230,324 records** (≈32×/≈21×); includes `MAL-*` malicious-package records; semver ranges. Records are stored under database-specific ids, **not every alias** — one issue can appear as several files (verified: lodash template-injection lives in two GHSA files, the CVE id is a 404 in the bucket). |
| Granularity of OSV | Package only | Package only, but **one record can carry many `affected[]` entries** — several npm packages at once (verified: the lodash record lists `lodash`, `lodash-es`, `lodash.template`, `lodash-template` with per-package ranges, plus a RubyGems entry that must be ignored) and entries without a `package` field. Matching iterates all npm `affected[]` entries; explicit `versions` may carry ecosystem suffixes (`4.17.20-npm`) which the matcher normalizes. Still needs `vuln-mappings.json`, now keyed by public export path. |
| Distribution | Fat JAR + GraalVM native (now 35.8 MB, single-arch linux/amd64; **no signing, no Release assets, no action.yml in the JVM repo**) | Bun-compiled binary per platform (**measured ~81 MB, ~4 ms cold start**), published to npm via per-platform packages, Docker image (multi-arch — a real improvement over the JVM single-arch image), GitHub Action. Supply-chain signing (SHA256SUMS, cosign, provenance) is **new work beyond the JVM tool, budgeted in M6 for v1 (v3.4 item 3; v3.5 item 4: template verification via a repo-pinned digest + cosign identity, never the release's own checksums)**; the macOS/Windows signatures (notarization, Authenticode) stay in M7d — **the v1 macOS/Windows binaries are experimental and unsigned (v3.5 item 4)**. |
| Isolation | Forked worker JVM | Self re-exec as worker process + Bun Workers for parse parallelism. **Worker constraint (measured 2026-10-13):** in a compiled binary a worker starts only when its file is a *separate compile entry* (embedded as `$bunfs/root/<name>.js`); a file that is both main and worker fails with `ModuleNotFound`. Data-URL workers are unsupported. Worker URLs are built from the main entry's `import.meta.url` with the original source filename; a lint + compiled-binary CI test pins this. |

Two concepts need re-definition because JavaScript executes module top-level code on import:

- **Package-level evidence tiers.** `LOADED` = the package's entry module is imported by reachable code. `CALLED` = a call edge crosses from code outside the package into the package (a call whose callee resolves into the package's IR: an API call or `new C()`). `LOADED` is the weaker evidence — more packages pass as REACHABLE, so it is noisier *and* stricter for the CI gate (more failures). `CALLED` is the default gate (the honest analogue of "some class of the artifact is reachable"). Reports always carry all three fields: each finding has `evidence: {loaded, called, callbackRegistered}` — **unambiguous (v3.4, item 10): `called` = direct call or `new` only; `callbackRegistered` = a package function passed as a value** (registration is its own field because registering a callback does not prove the callback ever executes; `callbackInvoked` tracking is a post-v1 limitation, listed in `limitations`). **The `call` tier is met by `called` *or* `callbackRegistered` by default; `--call-evidence=direct` requires direct calls only** (v3.4). The gate uses the tier selected by `--package-evidence=call|load` and never discards the other. **JS-only case (import time, v3.3):** a package whose vulnerability lives in import-time side effects can be LOADED without ever being CALLED — with the `module-init` node (§5.4) such code is *in the graph*: a mapping target executed at import time is REACHABLE at mapping level (`import → module-init → target`) even when the artifact is below the evidence tier; at the default `call` tier the artifact is UNREACHABLE with `installed: true` and a dynamic-risk NOTICE (below), so the limitation is visible, not silent.
- **Dynamic-risk notice** replaces `onClasspath`: a package that is installed but has no static path gets `UNREACHABLE` with `installed: true` and a NOTICE if the package could **plausibly be loaded** by an unresolved dynamic `require`/`import()`/`eval` — **scoped (v3.2): a marker in application code (which could load any installed package) or in a library module whose own dependency graph reaches that package; an unrelated global `eval` does not flag every installed package** (§5.6; console wording mirrors the JVM `onClasspath` NOTICE).

- **The clean-result principle (v3.3, the governing rule of this document):** a clean result means *no policy-triggering finding was established by the analysis*. It must not be presented as proof that every vulnerability is unreachable unless the analysis can substantiate that conclusion: `REACHABLE` is positive evidence of a path; `UNREACHABLE` is no path found *within the modeled subset* (dynamic behavior, missing sources, and opaque boundaries can hide paths — the report's `analysisStatus`, `completeness`, `exposure`, and `limitations` say exactly what could have hidden them, §5.6). The principle governs the verdict schema, dynamic-risk reporting, source-resolution policy, CI exit codes, and documentation from the first release: **a green run with `analysisStatus: PARTIAL` prints that, in the console, next to the verdict summary.**

## 3. Key decisions (each ADR now exists as a separate document — `docs/adr/0002`–`0017`; 0001 is the bootstrap record + index; v3.6)

1. **Language and runtime: TypeScript, strict mode, run on Bun, core stays runtime-agnostic.** All `Bun.*` APIs live behind a small `platform/` adapter so the core also runs under Node. This keeps Node-based branch-coverage gates (§9) and debugging possible.
2. **Own call-graph engine over an IR, not a wrapper around an existing tool.** Parsers produce a language-neutral per-file IR; the analysis consumes only the IR. [Jelly](https://github.com/cs-au-dk/jelly) (JS/TS flow-insensitive call-graph + vulnerability-exposure analyzer; TypeScript, BSD-3-Clause, **Node-only, CLI/server with no documented library API**) is evaluated in the M0 spike as a benchmark oracle, run under a pinned Node outside the binary. It cannot be the primary engine (Node-only, no public API), but its permissively-licensed sources are a design reference for the library models.
3. **Parser: TypeScript compiler API in parse-only mode (`ts.createSourceFile`) for everything, with `acorn` benchmarked as a fast path for plain `.js` in `node_modules`.** One library handles JS, TS, JSX, TSX; pure JS, so it embeds in the Bun binary on every target. Native parsers (oxc, swc) rely on per-platform `.node` addons that complicate cross-compilation; revisit if the M0 benchmark shows parsing dominates runtime. Full type checking needs `lib.*.d.ts` files; v1 avoids it (type-narrowing is a stretch item).
4. **Module resolution: own resolver with three explicit profiles (v3.3, callis ADR 0005 updated; v3.4 adds b2), not `Bun.resolveSync`** — Bun's resolution has its own conditions and quirks, and verdicts must be deterministic and runtime-independent. **(a) Runtime resolution** (authoritative for call edges): Node semantics — CJS + ESM, conditional `exports`/`imports` (condition ordering matters; nested conditions), package self-references and `#` imports, `main`/`index`, extension probing (`.mjs`/`.cjs`/`.mts`/`.cts`, the `type` field), workspaces, symlink and package-manager realpaths — **and no `tsconfig` `paths`/`baseUrl` at runtime: a TS alias that does not runtime-resolve must not invent a production call edge**. **(b) TS source mapping** (separate): `tsconfig` `paths`/`baseUrl` (and project references) map runtime modules back to their TS source files for location reporting only. **(b2) Application-code alias resolution (v3.4, item 1):** the v1 frameworks depend on `tsconfig` aliases *at runtime* — Next.js resolves `@/…` through its own compiler, Nest through its build (`tsc` + `tsc-alias`) — so **for application code only**, `paths`/`baseUrl` apply when the project shows a runtime-resolution mechanism (a Next.js config, a Nest build config, or a `tsconfig-paths`/`tsc-alias`/`module-alias` dependency); such edges are marked `resolution: "tsconfig-alias"` with degraded `confidence`; **an alias with no runtime mechanism stays unresolved** (the v3.3 negative fixture holds). M0 decides: apply b2, or drop Next/Nest from the v1 framework matrix. **(c) Bundler/framework-specific adapters** (post-v1, M7). Every resolution decision records the conditions, candidate paths, and the reason for the chosen target; **an unresolved module stays unresolved** — it is counted in `completeness.unresolvedImports` (§5.6), never silently fallen back to a convenient file. **Core modules (`fs`, `path`, `node:fs`, …) are resolved, not unresolved: the resolver classifies them as `builtin` (v3.5, item 2)** — and the status rule: **only unresolved imports in application code, or in a package that carries a candidate advisory, count toward `PARTIAL` (v3.5 item 2); an unresolved import elsewhere (a library's optional `try { require("bufferutil") }`, platform-specific modules, missing optional peers) is recorded in `completeness.unresolvedImports` + `limitations`, never the status** — those imports are ubiquitous in real dependency trees, and counting them all made `PARTIAL` the norm again. M2 pins the runtime profile against the actual resolution behavior of the supported Node versions (fixture matrix: conditional exports including ordering, self-references, `#` imports, require vs ESM, `type` field, symlinks, nested duplicates — **and the v3.4 alias pair (item 1): a `tsconfig` alias *with* a detected runtime mechanism must produce an edge marked `resolution: "tsconfig-alias"` (the Next/Nest fixture), while one *without* a mechanism must produce no edge**).
5. **Validation: Zod** (or Valibot) schemas for SBOM, OSV records, and `vuln-mappings.json`; any schema failure maps to exit `2`.
6. **CLI: `node:util` `parseArgs` plus a thin wrapper** (zero dependencies, works in Bun), unless M0 shows we need subcommand ergonomics, then `commander`.
7. **Lint/format: Biome** (single binary) plus `tsc --noEmit` with `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`. This replaces Checkstyle/SpotBugs.
8. **Distribution — v1 vs post-v1 marked (v3.5):** **release assets with checksums + cosign signatures + provenance attestation (M6, v1 — v3.4 item 3) and the multi-arch Docker image (M6, v1) ship in v1; per-platform npm packages (esbuild/Biome pattern, M7d) and the GitHub Action (M7e) ship post-v1 (v3.3 C1/C2).** **Brand (v3, user decision):** the tool is **`callis`** — binary `callis`, npm scope `@callis/*`, report `tool.name` "callis", cache dir `$XDG_CACHE_HOME/callis`, default `--output=callis-report`. The project and repository are **`callis-js`** (the repo keeps its current name — no rename). The JVM project's `reachability-analyzer` brand stays with the JVM tool; the two are sibling projects sharing the CI contract, not one brand.
9. **Bun pinned to 1.4.2** (latest stable verified 2026-10-13, satisfies the two-week minimum-age rule; see §8). M0 re-verifies against whatever stable exists then; every flag in §7 is measured on 1.4.2 and must be re-verified after any Renovate bump. **Runtime-adapter contract (v3.3, C8):** the identical core fixture suite (resolver, IR, verdicts, report writers) runs under **both** Bun and Node — the `platform/` adapter is the only difference between the two runs; the compiled-binary e2e tests remain a separate distribution gate.
10. **Soundness contract (v3.3):** the engine classifies every supported construct as *modeled / conservatively approximated / unsupported* (§5.5); unresolved behavior is explicit in the IR and propagates into `confidence`, `exposure`, and `limitations`; the 80% oracle floor is an acceptance gate, not evidence of safety; release criterion: **no claim of complete reachability** — the supported subset is documented and every material limitation is machine-readable.
11. **Verdict and completeness semantics (v3.3):** verdicts are evidence statements, not proofs (§2 principle); `analysisStatus` + `completeness` are mandatory report fields; the exit code is a policy decision over findings *and* completeness; the engine/policy split of §4 (structured `AnalysisResult` + a separately tested policy layer).
12. **Advisory normalization (v3.3):** OSV records normalize into per-package internal records; dedup merges only on verified identity + compatible ranges (union of ranges and source record ids), never on alias-set overlap; the canonical id is a presentation field; entries with no determinable package identity do not match.
13. **Install reconciliation (v3.3, refined v3.4, v3.5 items 1/7):** per-component states `RESOLVED | MISSING | VERSION_MISMATCH | AMBIGUOUS` (+ `NOT_CHECKED` in `--sbom-only`); `--strict-sources` covers every non-`RESOLVED` state; the deterministic install fingerprint joins the cache keys; `AMBIGUOUS` only when a component cannot be tied to any instance via the tie graph (item 6 — multiple instances of one name+version are the normal case, each with its own verdict; **v3.5 item 7: the tie graph is the SBOM `dependencies[]` when present, else the lockfile's resolved graph, else separate instances with `completeness.dependencyGraph: "absent"` — never `AMBIGUOUS` without a graph to check**); `VERSION_MISMATCH` matches the advisory against the **installed** version (item 7; v3.5 item 8: both versions evaluated, `matchedOn` label); **v3.5 item 1: reverse reconciliation — the graph's loaded instances are checked back against the SBOM; an instance with no SBOM component goes into `completeness.unlistedInstalled` + `PARTIAL`, and `--match-installed` extends candidate generation to the installed instances.**
14. **Cache keys (v3.3, split in v3.4, refined v3.5 item 5):** per-file IR key (content hash, tier 1); the **input key** — computable *before* the run (versions, SBOM, OSV pin, mappings, lockfile variants, install fingerprint, whole-tree application-source hash, flags; what `--print-cache-key` prints, §6); the **memo key** — post-run (entry-point set, resolved graph, loaded-file IR keys, model/resolver versions; internal, recorded as `keys.memo`); `--hash-installed` extends the input key; **the source exclusion list is the default — any directory containing a resolved entry point or a loaded application file is auto-included with a warning (v3.5 item 5), and `--source-exclude`/`--source-include` override it**; full-result caching disabled when installation integrity cannot be established; the cache read/write consumes the same canonical definition.
15. **Engine/policy separation (v3.3):** the engine produces a structured `AnalysisResult`; the policy layer maps it to exit codes; both are tested independently (§4).
16. **Threat model (v3.3, clarified v3.4):** trusted inputs — **the OSV source (the pinned `osv-vulnerabilities.storage.googleapis.com` URL), trusted for authenticity; the record contents it serves are still parsed as untrusted data** — plus user-provided SBOM/lockfile/mappings validated as data, and signed release artifacts with a documented verification path (**v1 actually produces them: M6, item 3; v3.5 item 4: the verification path is independent — the template pins the expected digest in the repo and runs `cosign verify` against an explicit certificate identity + OIDC issuer, never against a checksum fetched from the same release**); untrusted inputs (application source, `node_modules`, OSV record contents — parsed, never executed); explicit resource limits per class (§7). A checksum computed from the same untrusted artifact is not independent evidence of integrity.

## 5. Pipeline in detail

### 5.1 SBOM input

- Auto-detect CycloneDX (`bomFormat`) vs SPDX 2.x (`spdxVersion`). SPDX 3.x, unknown `bomFormat`, or neither marker: explicit error, exit `2` (JVM ADR 0016 parity).
- Extract npm components from purls (`pkg:npm/%40scope/name@1.2.3`; decode scope percent-encoding). Components without an npm purl are skipped with a warning (same contract as the JVM tool).
- Carry CycloneDX `scope` and the npm development-dependency property so dev-only packages can be labelled `DEV_ONLY` and excluded from analysis by default (`--include-dev` to analyze them). **Definition (v2):** a `DEV_ONLY` component is *reported, not analyzed*: it never enters the call graph, never counts in the reachable total, and has no exit-code effect unless `--include-dev` — **except the malware gate (v3.2 precedence): a dev-only component covered by a `MAL-*` record gets verdict `MALICIOUS_PACKAGE`** (the `--malware=fail` default applies — install scripts run on the CI machine regardless of scope), **and `MAL-*` components are excluded from the analyzable set the NO_SOURCE guard counts (§5.3)**. **Dev-marker detection (v3.2):** M1 verifies each recommended producer's marker (CycloneDX `scope`, cdxgen properties); SPDX 2.x has no scope field — map `DEV_DEPENDENCY_OF` relationships; **SBOMs without dev markers analyze every component** (no `DEV_ONLY` verdicts), the safe default. **`DEV_ONLY` means excluded from reachability analysis, not safe (v3.3):** build tools, test runners, code generators, and bundlers execute on CI — a vulnerable dev dependency is a real risk class; the `--malware` gate already ignores dev scope, and M5 adds fixtures for malicious install scripts, build plugins, test runners, and code generators. (JVM has no analogue — its SBOM parsers read **no** scope or dev-dependency property at all, so every component is analyzed regardless; this is a pure JS extension because `npm sbom` does include devDeps.)
- Keep the SBOM `dependencies[]` graph: it provides the human-readable supply path (`app → express → qs`) shown alongside the code-level trace. **(v3.5, item 7: when the SBOM carries no `dependencies[]` — common; SPDX 2.x files often lack one — the component→instance tie of §5.3 falls back to the lockfile's resolved graph, and if that is also unavailable, duplicate instances stay separate instances, never `AMBIGUOUS`, with `completeness.dependencyGraph: "absent"` recording the gap.)**
- Recommended producers: `npm sbom --sbom-format cyclonedx|spdx`, `@cyclonedx/cyclonedx-npm`, `cdxgen`.

### 5.2 OSV npm snapshot

- `scripts/download-osv.sh npm osv-npm` fetches `https://osv-vulnerabilities.storage.googleapis.com/npm/all.zip` (verified 2026-10-13: 200 OK, 218,363,616 bytes, refreshed at least daily) and writes the pin file. Reuse the pin algorithm exactly (sha256 over `name:filesha256` lines, sorted by **byte order** — `LC_ALL=C` in the script, UTF-8 byte comparison in TypeScript, never `localeCompare`) so the pin is identical between the shell script and the analyzer. **Performance note (v2):** 230k files make per-file hashing the slow step; both the script (batched `sha256sum`) and the runtime verification (parse pool) parallelize.
- **Index, do not scan.** OSV files are named by advisory id, not package. A full scan per run would be too slow on 230k records. First run builds `osv-index.json` (`package name → record files`, including all `aliases` of every record as a secondary key) in `--cache-dir` (default `$XDG_CACHE_HOME/callis`), **never inside `--osv-dir`** (it may be read-only or shared). The index header stores the snapshot pin; pin mismatch (or no `--osv-checksum` and a stale fingerprint) rebuilds. Later runs read only records for packages in the SBOM. (M0 measurement, 2026-10-13: 230,324 records / 208 MB; central directory 15 MB.)
- **Version matching:** implement OSV `SEMVER` ranges (`introduced`, `fixed`, `last_affected`, multiple events per range), honor explicit `versions` lists (normalizing ecosystem suffixes like `-npm`; some entries carry no `package` object — **an entry with no determinable package identity does not match (v3.3): the record's ecosystem only filters which records are read; it never establishes which package an advisory affects**), treat `ECOSYSTEM` ranges as semver for npm, and skip `GIT` ranges with a warning — **but only when no `SEMVER`/`versions` evidence remains for that `affected[]` entry** (verified records mix GIT ranges with explicit versions). A single record's multiple npm `affected[]` entries each produce their own candidate when their package appears in the SBOM. **Version choice under drift (v3.4 item 7, both versions v3.5 item 8):** when a component's state is `VERSION_MISMATCH` (§5.3), the matcher evaluates the affected ranges against **both versions — the installed one (what actually runs) and the SBOM one** — and a finding is kept if either is in range, labelled `matchedOn: installed | sbom | both`; the finding carries both `componentVersion` (SBOM) and `installedVersion`, and a version outside every affected range is reported as such (NOTICE — never silently green). **Pipeline order (v3.5, item 8): components are resolved (§5.3) *before* candidates are generated and matched** — so the stale-SBOM case (SBOM version outside every affected range, installed version inside — the tree drifted past the SBOM, not behind it) still produces a candidate and a finding; the zero-candidates shortcut and the total-resolution guard run after resolution. **Boundary semantics pinned (JVM ADR 0015 parity):** `introduced` is an inclusive lower bound, `fixed` is **exclusive** (`v == fixed` is not affected — the false-positive guard), `last_affected` is an inclusive upper bound; an event must carry exactly one of the three keys or the record is malformed (skipped + counted); an empty event list matches nothing; multiple events within a range AND, multiple ranges OR. Match evidence is recorded per candidate as `range#N (introduced=0, fixed=4.17.21)` or `versions` (the JVM `affectedRange` string shape). Property-test the matcher against the `semver` package on generated ranges.
- **Malicious packages (`MAL-*`):** reachability is meaningless for a package that is malicious at install time. Verdict `MALICIOUS_PACKAGE`, **default `--malware=fail` → exit 1** (a known-malicious component in the SBOM should fail CI by default; `warn`/`ignore` for triage workflows). `preinstall`/`install`/`postinstall` scripts are an informational NOTICE in all modes, never a failure by themselves. **Malware finding identity (v3.3):** each `MALICIOUS_PACKAGE` finding carries a stable id = canonical advisory id × package instance; malware findings are listed separately from reachability findings in the report summary; `--malware=warn|ignore` changes the exit code only — the finding is never suppressed; a `MAL-*` record that fails schema validation is skipped + counted, **never downgraded into a normal vulnerability with weaker policy**.
- **Normalization and dedup (v3.3, refined v3.4 item 8, callis ADR 0013):** the same issue can exist as several bucket files (verified: two GHSA files, the CVE id absent), and upstream data is inconsistent, so identity is established explicitly: every record normalizes into **per-package internal records** (source id, alias union, ecosystem, package identity, affected ranges, provenance); records merge only when **ecosystem + package identity match and the affected ranges are equal after normalization (v3.4: "compatible" defined)** — merging keeps the union of source record ids and aliases; **records with differing ranges for the same package are NOT merged: they remain separate findings, linked by `relatedIds` and grouped in the report** (e.g. two records covering different ranges of one issue). **Alias-set overlap is never the dedup rule** (partially overlapping alias sets can be distinct issues; slightly different sets can be the same one), and **the canonical id is a presentation field, not a dedup key**. Canonical id selection on the merged record: prefer the **lexicographically smallest `CVE-*` alias when several exist** (v2, completed v3.1), else the record's own `id`, else the lexicographically smallest alias; all aliases are listed in the report's `aliases` field. Pinned by golden tests (the lodash two-file case, a synthetic multi-`CVE-*` record) **and adversarial cases: partially overlapping alias sets (no merge), conflicting ranges across records (kept separate), conflicting package identities (no merge), an advisory lacking any package identity (matches nothing)**.

### 5.3 Project model: purl → code on disk

The resolver needs the actual install location of each component:

- **npm / Bun / Yarn with `nodeLinker: node-modules`:** walk `node_modules`, read each `package.json` (`name`, `version`), and match by purl. Nested duplicates (`a/node_modules/lodash@3` vs top-level `lodash@4`) are separate instances, each with its own verdict, and instances are **never collapsed by name+version alone**.
- **Resolution states (v3.3, refined v3.4 items 6–7, callis ADR 0014):** every SBOM component gets an explicit state in the report's `completeness` block (§5.6) — `RESOLVED` (directory with matching name+version), `MISSING` (the `NO_SOURCE` case), `VERSION_MISMATCH` (name present, installed version differs from the SBOM — the candidate is analyzed against the installed directory **and the advisory ranges are evaluated against the installed version** (§5.2, item 7), with a NOTICE and both versions on the finding), or `AMBIGUOUS` (**v3.4, item 6: a single SBOM component cannot be tied to *any* instance through the tie graph, even though instances with a matching name+version exist on disk; v3.5, item 7: the tie graph is the SBOM `dependencies[]` when present, else the lockfile's resolved graph — and when *neither* exists, duplicate instances stay separate instances, never `AMBIGUOUS` (no graph to check, no failure to report), with `completeness.dependencyGraph: "absent"` recording the gap**). **Multiple instances of one name+version are the normal case, not ambiguity:** nested hoisting and pnpm peer-dependency variants (same name+version, different store paths) are **separate instances, each with its own verdict on the app's resolved graph** — they never trip `--strict-sources` and are never collapsed; the install fingerprint records each instance's content, so drift between them stays visible. A deterministic **install fingerprint** — instance identities + realpaths + the install-state file content when present — is part of the cache keys (§6) and is compared against the lockfile's expectation, so locally patched packages, lockfile/tree drift, and unreadable directories are visible instead of producing apparently normal verdicts.
- **pnpm:** follow the symlinked `.pnpm` virtual store (`node_modules/.pnpm/<name>@<ver>/node_modules/<name>`).
- **Yarn PnP:** v1 refuses with exit `2` and a hint to use `nodeLinker: node-modules`; native `.pnp.cjs` support is a stretch item (M7c).
- **Workspaces:** treat each workspace package as application code; analyze entry points per workspace.
- **App-vs-library rule (v2):** a file is *library* if its **realpath** is under a `node_modules/` directory or the pnpm store (`.pnpm/…`); everything else under the project is *application code*. Symlinks resolve before classification, so pnpm's top-level links classify correctly and `nodeLinker: node-modules` Yarn/Bun need no special case.
- **npm aliases (`npm:foo@1`):** SBOM purls name the target package (npm lockfiles/SBOMs resolve the alias); matching is by `package.json` `name`+`version` in the installed directory, never by path — aliases need no dedicated code path (R7 gains an alias fixture).
- **Reverse reconciliation — installed instances not in the SBOM (v3.5, item 1):** reconciliation above runs SBOM→disk; the reverse direction is checked too. After the graph builds, **every package instance the call graph loaded is recorded; an instance with no matching SBOM component goes into `completeness.unlistedInstalled` and demotes `analysisStatus` to `PARTIAL`** — an SBOM generated from a stale lockfile or a different tree cannot silently omit a package the application actually loads (the v3.4 hole: such a package was never a candidate, never matched, and the run could exit 0 `COMPLETE`). A NOTICE names each unlisted instance (purl + instance path). New **`--match-installed` (v3.5):** also generate candidates from the installed instances, not only from SBOM × OSV — with it, an unlisted-but-loaded instance with an applicable advisory produces a finding (`source: installed`, the SBOM absence visible alongside); without it, the instance is still reported via `unlistedInstalled` + `PARTIAL` + the NOTICE — never a silent gap. Under `--sbom-only` there is no load set (no graph), so the check does not apply.
- Missing directory for an SBOM component yields verdict `NO_SOURCE` (analogue of `NO_CLASS_INFO`), **reported as a distinct verdict in all three formats (v2, deliberate deviation from the JVM report flattening — more useful here)** with a count in the console summary and a NOTICE. **Total-resolution failure guard (v3.1, defined over components in v3.2):** resolution status is computed **per SBOM component, independent of OSV matches, before the zero-candidates exit-0 shortcut** — a component with no advisories still has a resolution status, so a zero-candidate run cannot pass silently on a missing install. A component resolves by walking up from the project root through ancestor `node_modules` directories (npm hoisting: a monorepo subfolder finds its dependencies at the repo root), so a `--project` at a subfolder does not trip the guard wrongly; the per-candidate `NO_SOURCE` verdict and this per-component status share one resolver. If at least one analyzable (not `DEV_ONLY`, not `MALICIOUS_PACKAGE`) component exists and *every* analyzable component is non-`RESOLVED` (v3.3: missing, version-mismatched, or ambiguous), the run **exits `3` by default** with a message naming the likely cause (absent `node_modules`, wrong lockfile, unreadable mount) **and a minimal report in the selected formats listing each unresolved component (purl + directories tried), so the CI artifact explains the failure** — a run in which nothing resolved is a broken environment, never a clean one. `--strict-sources` extends the failure to *any* non-`RESOLVED` component (v3.3: version mismatch and ambiguity included, not only missing directories); `--sbom-only` (§6) disables the guard for SBOM-only workflows — that mode skips filesystem reconciliation entirely (**every component's state is `NOT_CHECKED`, not `NO_SOURCE`, v3.4 item 9**), and its `NOT_PERFORMED` status says so (§5.6). **Empty-SBOM guard (v3.4, item 12, refined v3.5 item 6):** if the SBOM contains **zero npm components at all, before dev filtering** (wrong producer, all non-npm purls), the run **exits `3`** — a run that analyzes nothing is a broken input, never a clean one; the explicit opt-out `--allow-empty-sbom` exists for pipelines that deliberately analyze non-npm SBOMs. **An all-dev SBOM (npm components, every one `DEV_ONLY`) is *not* empty: it exits `0` with the `DEV_ONLY` verdicts listed and an explicit NOTICE ("all components dev-only — use `--include-dev` to analyze them")** — the v3.4 wording fired the guard on a perfectly valid SBOM. **The guard applies under `--sbom-only` too (v3.5 item 6):** a supply-chain gate run against a component-less SBOM is broken input either way (`--allow-empty-sbom` overrides in both modes). **This is what actually closes the "silently green" hole the Docker README documents**: a CI job that forgets `npm ci` can no longer exit 0 with every component `NO_SOURCE`.

### 5.4 Front end and IR

Per-file extraction produces a serializable IR; nothing downstream sees an AST.

- **Module summary:** imports (ESM static, `import()`, `require` with literal argument, resolved lazily), exports (named, default, `export *`, `module.exports =`, `exports.x =`, `Object.defineProperty(exports, ...)`, Babel/TS interop helpers `__exportStar`, `__importDefault`), top-level statements (executed on load). **Module-init node (v3.3):** every module has a `module-init` node in the graph, connected from each of its importers by the import edge; top-level statements belong to `module-init` — **import-time side effects are in the graph** (mapping-level consequence in §5.6: a target executed at import time is reachable via `import → module-init → target` even when the artifact is below the `call` evidence tier).
- **Function summaries:** declarations (function, arrow, method, getter/setter, class constructor, generator, async), qualified names, parameters, returns, call sites (callee expression shape, argument shapes, `new`, optional call, tagged template), assignments relevant to function-valued flow (`a.b = fn`, `Foo.prototype.m = fn`, object literals, class fields).
- Handle UMD wrappers and IIFEs by normalizing to ordinary function summaries.
- IR files are cached on disk keyed by the **per-file IR key — `sha256(file contents)` + parser version + `IR_VERSION` + parse options (v3.3, the first of the three cache-key tiers, §6)** (`--cache-dir`, default `$XDG_CACHE_HOME/callis`). `node_modules` rarely changes, so warm runs skip almost all parsing; and because the key hashes *content*, an in-place patch of a loaded package changes its IR key and invalidates every derived result (P0.4/P0.7).
- Parsing runs in a pool of Bun Workers. **Compile constraint (measured 2026-10-13, §7):** worker entry files are passed as additional compile entries; the worker URL is `new URL("<worker-source-filename>", <main entry import.meta.url>)` (the main entry embeds as `$bunfs/root/<outfile-base>`, workers as `$bunfs/root/<name>.js`); a worker may never be the same file as the main entry, and no `data:`-URL workers — both pinned by a lint rule and a compiled-binary CI job that asserts the pool actually executes.

### 5.5 Call-graph construction

Demand-driven worklist from the entry points. Only modules reachable through the resolved import graph are ever loaded, so a 30,000-file `node_modules` costs only what the application actually touches.

**Default mode (RTA-analogue, field-based, flow-insensitive).**

1. Resolve direct calls: identifiers bound to local declarations or imported bindings go through the module export tables (cross-module, including re-exports and namespace imports).
2. `new C()` marks `C` as instantiated; `x.m()` resolves to methods named `m` on instantiated classes/prototypes (the RTA pruning idea) filtered by the receiver's known flow set where available.
3. Function values flow through assignments, arguments, returns, and exports (a lightweight 0-CFA); invoking a parameter calls whatever functions were passed to it.
4. **Library models** (`packages/models`, JSON, embedded via `--asset`): `Array.prototype.map/forEach/reduce/...`, `Promise.then/catch/finally`, `async/await`, `setTimeout/setInterval/queueMicrotask/process.nextTick`, `EventEmitter.on/once/emit` paired by literal event name, `fs.*` callbacks, `util.promisify`, `Function.prototype.call/apply/bind`, `Reflect.apply`, `Object.assign`/spread mixins, `super`, getters/setters. **Callback registration through user-defined wrappers** resolves only when the wrapper is in the catalogue; otherwise the registration site carries an unscoped dynamic marker (soundness contract, below). The model format is declarative so contributors can extend it without touching the engine.
5. Unresolvable constructs are recorded, never dropped: `require(expr)`, `import(expr)`, computed `obj[expr]()`, `eval`, `new Function`. Each becomes a **dynamic-risk marker** on the nearest reachable function (package attribution for the `exposure` metric and the §2 NOTICE: §5.6). Computed calls with a string-literal-set key resolve to those names; others fall back to name-based matching only when `--over-approximate-dynamic` is set.

**Soundness contract (v3.3, callis ADR 0011):** the engine's behavior on every supported construct is classified — **modeled** (direct/flow edges, 0-CFA, library models), **conservatively approximated** (name-based fallback under `--over-approximate-dynamic`; `--cha`), or **unsupported** (recorded, never dropped) — and the classification is part of the release notes, not folklore. Known unsupported forms include `Proxy` traps, dependency-injection containers, framework-generated dispatch, decorators beyond the modeled registrations, **re-assignment of a function or export after its initial definition** (the flow analysis is flow-insensitive: the last assignment wins, earlier aliases are lost), and **callbacks registered through unmodeled wrappers** (unscoped marker instead). Unresolved behavior is explicit in the IR and propagates: affected findings carry degraded `confidence`, and constructs that cannot be attributed to any package are counted in `exposure.dynamicUnscoped` (§5.6) — **reported separately from package-scoped dynamic risk, because they cannot be scoped to one**. The micro-benchmark corpus (§9) must cover the real-world edge forms — indirect calls, export mutation, dependency injection, wrapper callbacks — with positive *and* negative cases per framework. **Release criterion (v3.3): no claim of complete reachability** — the report and docs state the supported subset, and every material analysis limitation of a run is visible in machine-readable output (`limitations`, §5.6).

**`--cha` (names mode):** `x.m()` targets every function or method named `m` in loaded modules, dead code included. Over-approximates; use to compare, not to pass (same guidance as the JVM tool). `--cha` and `--pointer-analysis` together ⇒ exit 2 (JVM parity).

**`--pointer-analysis`:** Andersen-style inclusion-based points-to solver with object sensitivity over the same IR, adding an edge only when the receiver can actually point at the target. Opt-in, slower, stretch milestone (M7a).

**Entry points** (curated, extensible via `--callback-interfaces=<module#export,…>` and `--entry-points=<module#export,…>`):

- `package.json` `main`, `module`, `exports`, `bin` of the application package.
- **`package.json` `scripts` (v2):** resolve at least `start` to file entry points — a plain `node scripts/deploy.js` app with no framework and no `main` must not analyze to zero entry points silently.
- Server frameworks: Express/Koa/Fastify/Hapi route registration (`app.get(path, handler)`), NestJS decorators (`@Controller`, `@Get`, `@Post`, `@MessagePattern`), Next.js route files (`app/**/route.ts`, `pages/api/**`), SvelteKit/Remix/Nuxt server routes (config-driven pattern list).
- Serverless: AWS Lambda `handler` exports, Cloudflare/Vercel edge handlers.
- Async consumers: BullMQ `Worker`, KafkaJS `consumer.run({ eachMessage })`, amqplib `consume`, cron decorators and `node-cron` registrations.
- Test files are excluded unless `--include-tests`.
- **Semantics (v2):** `--entry-points` tokens **extend** the curated detection; `--entry-points-only` replaces it (the JVM replace contract). Malformed/unknown tokens warn, not fail (JVM `resolveOverrides` parity). **Zero entry points from all sources ⇒ exit 3** (analysis failure, not usage — JVM ADR 0009 parity) with a console list of exactly what was tried.
- The "every function is an entry point" variant is deliberately not offered (it destroys precision; same reasoning as the JVM tool's A13, which rejects "all interface implementations" for the same RTA-collapsing reason).

**Debugging surface (v2, JVM parity):** hidden `--dry-run-sbom` (parse SBOM, print component table), `--dry-run-match` (**SBOM + resolution + OSV match — the v3.5 item 8 order** — print candidate table; zero-valid-records dir ⇒ exit 3), `--dry-run-graph` (build call graph, print entry points + node/edge counts; zero entry points ⇒ exit 3). All exit 0 on success.

### 5.6 Targeting a vulnerability and issuing a verdict

Per candidate (advisory × installed instance, with the per-record `affected[]` iteration of §5.2):

- **Artifact-level default:** `REACHABLE` when the package reaches the configured evidence tier (§2). Coarse but low-false-positive, and honest given OSV carries no symbol data for npm (verified).
- **Mapping-level precision via `vuln-mappings.json`**, keyed by canonical advisory id and expressed against the package's *public* surface, because internal file names change between versions:

```json
{
  "CVE-2021-23337": [
    {"package": "lodash", "export": "template"}
  ],
  "CVE-2021-44906": [
    {"package": "minimist", "export": "default"}
  ],
  "EXAMPLE-INTERNAL": [
    {"package": "foo", "file": "lib/parse.js", "function": "parseHeader"}
  ]
}
```

`export` resolves through the package entry's export table (subpath exports like `lodash/template` supported) to a function node; `file` + `function` addresses internals. **Import-time targeting (v3.3):** a mapping target executed at import time is REACHABLE — the trace reads `import → module-init → target` (§5.4) — even when the artifact is below the configured evidence tier: **the absence of a cross-package call edge is not evidence that the code does not execute**; the `evidence` fields and the console state the basis. A mapping entry absent from the call graph is `UNREACHABLE`, not an error; a mapping id matching no SBOM candidate is a warning, never fatal (JVM parity). Validation at startup; malformed means exit `2` (JVM parity — the JVM schema is `id → [{class, method, descriptor?}]`, strict; the JS schema above re-shapes the target fields to the JS surface but keeps the contract).
- **Node identity:** `pkg@version::relative/path.js::Qualified.name`, stable across runs, used in traces and SARIF logical locations.
- **Verdicts:** `REACHABLE`, `UNREACHABLE`, `NO_SOURCE`, `DEV_ONLY`, `MALICIOUS_PACKAGE`, `NATIVE_OPAQUE` (path ends at a `.node`/WASM boundary the analysis cannot see into; **reported with `opaque: true`, never a failure by itself** — the v2 default, now the `--opaque-native=warn` default). **Native boundaries are graph nodes (v3.3, callis ADR 0012):** the boundary carries the native package, the exported symbol when available, and the incoming JS call sites, and distinguishes `nativeBoundary: "reached"` (application code reaches the exported interface of a package an advisory covers — a plausibly exploitable path, **fail-closed under `--opaque-native=fail`**) from `nativeBoundary: "unresolved"` (the analysis cannot establish whether the specific native function is reached) — **the engine not seeing into a component is never equated with the vulnerable component being unreachable**. **Verdict precedence (v3.4, item 11): `REACHABLE` wins whenever the evidence tier is met** — a call into a covered addon's JS wrapper satisfies the `call` tier, so the finding is `REACHABLE` (exit 1 by default); **`NATIVE_OPAQUE` applies only when the path ends at a boundary beyond which the vulnerable code cannot be seen *and the tier is not otherwise met* (the boundary crossing is the only evidence)** — informational under the default `--opaque-native=warn`, fail-closed under `fail`. **`MALICIOUS_PACKAGE` applies regardless of dev scope (v3.1):** a malicious devDependency still executes its install scripts on the CI machine at `npm ci` time, so the `--malware=fail` default covers it; `DEV_ONLY` affects reachability analysis only, never the malware gate.
- **Confidence (new, no JVM analogue):** each REACHABLE carries `PRECISE` (all hops resolved by direct/flow edges) or `NAME_BASED` (at least one hop came from a name-based fallback), so teams can choose to gate only on `PRECISE`. Also serialized: `matchLevel: "method" | "artifact"` (JVM computes `MatchLevel` but never reports it; reporting it is a deliberate improvement).

**Analysis completeness (v3.3, refined v3.4 item 5, callis ADR 0012) — independent of findings, independent of policy:** every report carries `analysisStatus` — `COMPLETE` (every component `RESOLVED`, no *counting* unresolved imports — v3.5 item 2: builtins are resolved, and only application-code or candidate-carrying-package imports count — graph fully built, every loaded instance listed in the SBOM; **v3.4: dynamic markers never demote the status — they belong in `exposure`/`limitations`, because nearly every real project has some, and the old definition would have made `PARTIAL` the norm and the status noise**), `PARTIAL` (≥1 component non-`RESOLVED`, or ≥1 counting unresolved import (v3.5 item 2), or ≥1 loaded instance not listed in the SBOM — `unlistedInstalled`, v3.5 item 1), `INCOMPLETE` (total-resolution guard fired, or graph construction failed), `NOT_PERFORMED` (`--sbom-only`) — plus a `completeness` block: per-component resolution states, `unresolvedImports` (**v3.5 item 2: all unresolved imports with their location class — app code / candidate-carrying package / library-optional — only the first two count toward the status**), `dynamicUnscoped`, `opaqueBoundaries`, `graphBuilt`, `unlistedInstalled` (v3.5 item 1), `dependencyGraph: present | absent` (v3.5 item 7), each with reasons. **`--require-complete` (v3.4): exit `3` when the status is `PARTIAL` — the strict-CI opt-in; the default stays exit 0 with the status visible.** **The exit code is a policy decision over findings *and* completeness (v3.3):** defaults preserved (a `PARTIAL` run with no reachable finding exits 0), but **a report must never imply complete analysis just because no `REACHABLE` finding was found** — the console prints `analysisStatus` next to the verdict summary, and the state is visible in all three formats. **Schema versioning (v3.3):** the report carries `schemaVersion`, **independent of `toolVersion`** (a tool release does not necessarily change the schema; a schema change does not necessarily change the analysis); field classes (mandatory / optional / extensible) are documented; SARIF is pinned to 2.1.0; unknown verdicts and properties stay forward-compatible. **`limitations` (v3.3):** a machine-readable array of this run's material analysis limitations (soundness-contract unsupported forms actually encountered, the import-time caveat, the `callbackInvoked` gap, native opacity) — so a consumer sees exactly which negative conclusions are qualified.
- **Report shape (v2, JVM parity + extensions):** JSON entries carry `id` (canonical, §5.2), `aliases`, `purl`, `component`, `componentVersion`, `verdict`, `installed`, `evidence {loaded, called, callbackRegistered}` (v3.3, unambiguous v3.4), `resolutionState` (v3.3, §5.3), `installedVersion` (v3.4 item 7, on `VERSION_MISMATCH`), `matchedOn` (v3.5 item 8, `installed | sbom | both` — which version(s) the range match used), `source` (`sbom` | `installed`, v3.5 item 1 — on `--match-installed` findings the SBOM never listed the instance), `nativeBoundary` (v3.3, on `NATIVE_OPAQUE`), `relatedIds` (v3.4 item 8, unmerged sibling findings), `matchLevel`, `confidence`, `summary`, `severity`, `affectedRange` (matcher evidence string), `path` (empty when not reachable), `supplyPath` (SBOM `dependencies[]` chain). `NO_SOURCE` remains a distinct verdict (console NOTICE wording mirrors the JVM `onClasspath` NOTICE; like the JVM `NO_CLASS_INFO`, a single `NO_SOURCE` finding has **no exit-code effect** — only REACHABLE triggers exit 1 — the exit-code consequences come from the component-level rules: the total-resolution guard (§5.3), `--strict-sources`, and the `2 > 3 > 1 > 0` precedence (§1)). Report metadata carries the JVM parity fields: `toolVersion`, `callGraphBuilder` (policy), `entryPointCount`, `callGraphNodes`/`callGraphCalls`, `osvSnapshotSha256`, `osvSkippedRecords`, `sbomFile`, `durationMillis` — no wall-clock timestamps anywhere; `durationMillis` is excluded from cache keys and the binary-parity comparison (§9). **`exitReasons[]` (v3.5, housekeeping):** every condition triggered in this run — `REACHABLE_FINDINGS`, `MALWARE_FAIL`, `OPAQUE_NATIVE_FAIL`, `TOTAL_RESOLUTION_GUARD`, `EMPTY_SBOM_GUARD`, `STRICT_SOURCES`, `REQUIRE_COMPLETE`, `ANALYSIS_FAILURE` — **independent of the precedence winner**: a run that has both a REACHABLE finding and a guard failure exits 3 (precedence `2 > 3 > 1 > 0`) *and* lists both reasons, so CI that routes exit 1 to the security queue and exit 3 to the platform queue reads this array, not the exit code alone (documented in the README, M6). **`exposure` (v3.1 `dynamicRiskCount`, generalized v3.2, extended v3.3 — all false-negative exposure):** metadata carries `exposure: {dynamicRisk, noSource, nativeOpaque, dynamicUnscoped, loadedNotCalled}` and the console prints the one-liner (`exposure: N dynamic-risk, M no-source, K native-opaque, U unscoped, L loaded-not-called`) so a reviewer sees the exposure without opening every finding. **`loadedNotCalled` (v3.4, item 13):** the count of packages LOADED but below the configured evidence tier — imported, never called: the **import-time exposure that unmapped advisories cannot see** (most npm advisories have no mapping, so this count is the reviewer's signal that the default `call` tier is not gating on load-time behavior). `dynamicUnscoped` (v3.3): unresolved dynamic constructs **not attributable to any particular package** (e.g. a global `eval` in application code) — reported separately from package-scoped risk (§5.5 soundness contract). **`dynamicRisk` (scoped, v3.2):** UNREACHABLE findings whose package could **plausibly be loaded** by an unresolved dynamic construct — a dynamic `require(expr)`/`import(expr)`/`eval` in **application code** (which could load any installed package), or in a **library module whose own dependency graph reaches that package**; a marker in a library that does not depend on the package does not count (without this scoping, one global `eval` would flag every installed package — this is also the NOTICE scoping of §2). `noSource`: unresolved components (the §5.3 guard map). `nativeOpaque`: findings ending at a `.node`/WASM boundary. Note: the JVM tool never parses the SBOM `dependencies[]` graph (no supply path in its reports); `supplyPath` is a JS extension.
- Call traces: shortest path entry → vulnerable node (multi-source BFS, lexicographic-first tie-break — JVM ADR 0006 pinning, so identical graphs yield identical traces), plus the SBOM supply path.

## 6. CLI contract

All options from the JVM tool carry over with `--app-classes` and `--classpath-file` replaced by `--project` and `--java-version` dropped:

| Option | Meaning |
| --- | --- |
| `--project=<dir>` | Project root (defaults to cwd); source of `package.json`, `tsconfig.json`, `node_modules`. Missing dir ⇒ exit 2 (JVM `--app-classes` parity). |
| `--sbom` | SBOM file (CycloneDX 1.4–1.6 or SPDX 2.x, auto-detected). Required; unreadable/malformed ⇒ exit 2. |
| `--osv-dir` | Directory with local OSV npm records. Required; unreadable ⇒ exit 2; files-but-zero-valid-records ⇒ exit 3. |
| `--osv-checksum=<sha256>` | Expected pin; mismatch or hash failure ⇒ exit 2 (JVM parity). |
| `--mappings` | Optional `vuln-mappings.json`; malformed ⇒ exit 2. |
| `--entry-points=<module#export,…>` / `--entry-points-only` | Extend / replace the curated entry points (v2 semantics, §5.5). |
| `--callback-interfaces=<module#export,…>` | Extend the curated callback list (JVM `class#method,…` shape, JS token). |
| `--cha` / `--pointer-analysis` | Mutually exclusive precision modes (together ⇒ exit 2). |
| `--package-evidence=call\|load` | Artifact-level evidence tier (default `call`); the `call` tier is met by a direct call *or* a callback registration (`evidence`, §2). |
| `--call-evidence=any\|direct` | Which evidence satisfies the `call` tier (v3.4): `any` = `called` or `callbackRegistered` (default); `direct` = `called` only. |
| `--include-dev`, `--include-tests` | Widen the analyzed set. |
| `--malware=fail\|warn\|ignore` | Policy for `MAL-*` records (default `fail`). |
| `--fail-on-applicable` | In `--sbom-only` mode, fail (exit 1) on any *applicable* non-malicious advisory (v3.4 item 9); without it, only `MAL-*` affects the exit code. **Outside `--sbom-only` it is a usage error (exit 2, v3.5 item 6)** — a full run's exit code already reflects reachability, and the flag's candidate-level gate has no meaning outside the SBOM-only contract. |
| `--strict-sources` | Any component in a non-`RESOLVED` state (missing, version-mismatched, or ambiguous, §5.3) becomes exit `3` (v3.3 — previously missing only). |
| `--require-complete` | Exit `3` when `analysisStatus` is `PARTIAL` (v3.4 item 5) — the strict-CI opt-in; the default is exit 0 with the status visible. |
| `--allow-empty-sbom` | Opt-out of the empty-SBOM guard (v3.4 item 12, refined v3.5 item 6): permits a run with **zero npm components before dev filtering** to exit 0 (an all-dev SBOM needs no opt-out — it exits 0 with the `DEV_ONLY` NOTICE anyway). |
| `--match-installed` | Also generate candidates from the **installed instances**, not only from SBOM × OSV (v3.5 item 1) — an instance the graph loaded but the SBOM never listed can then produce a finding (`source: installed`); without it, such instances are reported via `completeness.unlistedInstalled` + `PARTIAL` + NOTICE, never silently skipped. |
| `--source-exclude` / `--source-include` | Override the input-key source exclusion list (v3.5 item 5, §6 `--print-cache-key` item 7). The default list is a default: any directory containing a resolved entry point or a loaded application file is auto-included with a warning regardless. |
| `--opaque-native=fail\|warn\|ignore` | Policy for `NATIVE_OPAQUE` findings whose boundary is *reached* by a package an advisory covers (v3.3, §5.6): `fail` fails closed (exit 1), `warn` is the default (reported only), `ignore` suppresses the exit-code effect only — the finding is never removed. |
| `--sbom-only` | SBOM×OSV only: candidate-level verdicts (`MALICIOUS_PACKAGE`, `DEV_ONLY`) with **`resolutionState: NOT_CHECKED` for every component (v3.4 item 9: no filesystem in this mode — `NO_SOURCE` is dropped, not misused)** and no call-graph construction — for supply-chain gates that run without `node_modules` (e.g. a MAL-only check). The total-resolution guard is disabled in this mode; the report carries `noCallGraph: true` **and `analysisStatus: "NOT_PERFORMED"` (v3.3 contract): no `REACHABLE`/`UNREACHABLE` verdicts are emitted — only advisory applicability and malware status — and the SARIF/JUnit outputs must not present the result as a successful reachability check**. **Exit-code policy (v3.4): without `--fail-on-applicable`, only `MAL-*` affects the exit code — applicable non-malicious advisories are reported but do not fail; with it, any applicable advisory exits 1. The empty-SBOM guard applies in this mode too (v3.5 item 6: a component-less SBOM is broken input even for a supply-chain gate; `--allow-empty-sbom` overrides).** |
| `--cache-dir=<dir>` | IR and OSV-index cache (default `$XDG_CACHE_HOME/callis`). |
| `--over-approximate-dynamic` | Name-based fallback for unresolved computed calls. |
| `--format=<a,b,…>` | `json\|junitxml\|sarif`, default `json,junitxml` (JVM parity); unknown token ⇒ exit 2. |
| `--output=<base>` | Report base name, default `callis-report` (brand; the JVM default was `reachability-report`); not writable ⇒ exit 3. |
| `-v`, `--verbose` | Single boolean (no levels — JVM parity): entry-point list, graph stats, timing, `reports written`. |
| `--print-cache-key` (M8) | Prints the **input key — computable *before* the run (v3.4, callis ADR 0015)**: `sha256` over a sorted, canonical concatenation of (1) `toolVersion` + `IR_VERSION` + `schemaVersion` (a tool upgrade must never reuse a stale result); (2) the SBOM file sha256; (3) the OSV snapshot pin; (4) the mappings file sha256; (5) **every lockfile variant present** (`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`/`bun.lockb`) as `path:sha256` lines; (6) the **install fingerprint** (§5.3: instance identities + realpaths + install-state file when present, e.g. npm's `node_modules/.package-lock.json`, pnpm's `.modules.yaml` — exact names verified in M8), **extended by `--hash-installed` to content hashes of every installed file** — without it, task-level caching cannot see an in-place patch (documented caveat); (7) the **whole-tree application-source hash** (`path:sha256` lines; default exclusion list: `node_modules/`, `.git/`, `dist/`, `build/`, `.next/`, `coverage/`, `.turbo/`, the cache dir — **the list is a default, v3.5 item 5: any directory that contains a resolved entry point or a loaded application file is auto-included with a warning** (a Nest or Next app whose `main` points into `dist/` analyzes those files, so edits there must change the key), **and `--source-exclude`/`--source-include` override the default**); (8) the effective policy as canonical JSON. **The memo key (v3.4, internal — known only after the run, recorded in the report as `keys.memo`)** is `sha256` over the entry-point set, the resolved dependency graph, the per-file IR keys of every loaded file, the library-model version, the resolver version + profile, and the graph-policy flags; **it is what callis's internal call-graph memoization consumes**, and because tier-1 IR keys hash *content*, an in-place patch of a loaded package invalidates every derived result even when name, version, and install state are unchanged. **When installation integrity cannot be established** (no lockfile and no install-state file), full-result caching is disabled for the run (a warning is printed; per-file IR caching still applies). **The real cache read/write paths consume this same canonical definition** (M8 round-trip test; the invalidation matrix covers source edits, lockfile edits, in-place package patches, mapping changes, model changes, and tool upgrades). For Turborepo/Nx recipes (post-v1, M7e) — the input key is the pre-run task hash. New — the JVM tool has no equivalent. |
| `--hash-installed` | Include content hashes of every installed file in the input cache key (v3.4 item 2) — without it, task-level caching (Turborepo/Nx) can miss an in-place package patch; documented. |
| `--dry-run-sbom` / `--dry-run-match` / `--dry-run-graph` | Hidden debugging trio (JVM parity, §5.5). |

**Exit-code precedence (v3.2):** `2 > 3 > 1 > 0` — usage/config errors first, then analysis failures (total-resolution guard, `--strict-sources`, OOM, non-writable `--output`), then reachable findings; a run exits 3 even when reachable findings also exist, and the report lists both. On guard failure a **minimal report is written in the selected formats listing each unresolved component (purl + directories tried)**, so the CI artifact explains the failure (stale-report deletion still runs first).

## 7. Bun build and distribution

**Compile command (per target, measured working on Bun 1.4.2, 2026-10-13):**

```bash
bun build --compile --minify --sourcemap \
  --target=bun-linux-x64 \
  --no-compile-autoload-dotenv --no-compile-autoload-bunfig \
  --define BUILD_VERSION='"0.1.0"' \
  packages/cli/src/main.ts packages/core/src/worker/parse-worker.ts \
  --outfile dist/callis-linux-x64
```

Measured facts (this machine, 2026-10-13, Bun 1.4.2) that settle the former open points:

- **Targets:** one build job emits `bun-linux-x64`, `-linux-arm64`, `-linux-x64-musl`, `-linux-arm64-musl`, `-darwin-x64`, `-darwin-arm64`, `-windows-x64` — all cross-compiled from a single linux-x64 host and verified as valid ELF/Mach-O/PE. The **`bun-linux-x64-baseline`** variant (no AVX2) exists and is included. Smoke-test each on a native runner afterwards. **Supported v1 platform (v3.5, item 4): Linux — glibc and musl, x64 and arm64, plus the no-AVX2 baseline build. The macOS and Windows binaries ship in v1 as *experimental and unsigned*: smoke-tested on native runners, but notarization and Authenticode land with M7d, so unsigned macOS/Windows releases carry a clear "experimental, unsigned" label in the release notes and README.**
- **Config autoload is a security issue and the flags exist.** Standalone executables autoload `.env` and `bunfig.toml` from the cwd **by default**; `tsconfig.json`/`package.json` autoloading defaults off. Compile with `--no-compile-autoload-dotenv --no-compile-autoload-bunfig` and keep the hostile-cwd test: plant a `bunfig.toml` and `.env` in the analyzed project, assert no behavior change, run against the **compiled binary** in CI.
- **Embedded data:** curated lists and library models are `--asset`-embedded (flag verified) so the binary is self-contained. A test runs the binary from an empty directory with the source tree absent.
- **Workers:** as in §5.4 — separate compile entries, URL from the main entry's `import.meta.url`, same-file-as-main forbidden, no `data:` URLs; a compiled-binary CI job exercises every parallel path (the plan's original requirement, now with the exact measured failure mode to pin).
- **Native addons:** the dependency policy is *no `.node` addons in the core*. A CI check fails if the bundle graph contains one.
- **Size and startup (measured, not promises):** hello-world binary = **81,315,296 bytes** on every target; `--bytecode` changes nothing (identical size). Expect the real tool at **~85–95 MB** (it embeds the TS compiler API). Startup: **~4 ms** for a trivial script — no cold-start penalty versus the JVM native image (3–13 ms `--version`). Record exact size/latency per target in release notes.
- **Memory:** JavaScriptCore has no `-Xmx`. Process isolation comes from re-executing the binary as a worker (`process.execPath` with a hidden `--internal-worker` mode); memory pressure is bounded by the container/cgroup limit, optionally with Bun's reduced-memory mode passed through compile-time exec args. The worker announces its pid (`callis: analysis runs in process <pid>`; the JVM tool's message shape carries over, the prefix is the brand's) so OOM kills are attributable.

**Threat model and hardening (v3.3, clarified v3.4 item 14, callis ADR 0017):** the **trusted** inputs are **the OSV source — the pinned `osv-vulnerabilities.storage.googleapis.com` URL — trusted for authenticity; the record contents it serves are still parsed as untrusted data (§3.16)**, the user-provided SBOM/lockfile/mappings (validated, treated as data), and the signed release artifacts (**v1 actually produces them — M6, item 3**) — **and signing is only as good as a documented verification path**: the README explains how to verify cosign/provenance, and the signing identity is independently established. **Untrusted** inputs are the application source, `node_modules`, and OSV record contents — parsed, never executed. One subtlety pinned explicitly: **the pin `download-osv.sh` computes from the archive is not independent evidence of integrity** — the user pins it because they trust the source; the report records pin + snapshot refresh date so a poisoned snapshot is at least identifiable later. Controls for the untrusted classes: parse-only (no `require` of target code), config autoload off (measured, above), and the **explicit resource limits (v3.3, P1.5): per-file byte caps, total parsed-byte caps, graph node/edge caps, bounded worker concurrency, per-worker timeouts with a cancellation protocol; OSV-archive unpacking validates entry paths and rejects traversal; JSON readers bound nesting and reject oversized or malformed records; an intentional limit hit is diagnosed distinctly from an OOM kill** (both map to the documented analysis-failure policy, exit 3). Bun's reduced-memory option is verified in M0 before it enters the isolation contract — a container memory limit is an external constraint, not a guarantee of graceful failure.

**Distribution channels:**

1. **npm** (`@callis/cli`) — **post-v1, M7d (v3.3 C2):** v1 ships the standalone release binary + the `callis-check.yml` template; the npm install experience ships with the M7d package layout. The esbuild/Biome pattern: a tiny JS shim plus `optionalDependencies` on `@callis/cli-linux-x64`, `-linux-arm64`, `-darwin-arm64`, `-win32-x64`, etc., each containing one binary with the `os`/`cpu` (and `libc` for the musl variants) fields that select it — the platform set covers the glibc **and** musl builds for linux x64/arm64 **and** the `baseline` (no-AVX2) x64 build, as §7's target list produces. `npx @callis/cli` and `devDependencies` installs work; the shim runs under any Node (or Bun) and the binary is plain native — no runtime requirement beyond the shim. The template downloads the pinned `callis` binary from the M6 GitHub Release assets and verifies the digest pinned in the repo (not the release's own `SHA256SUMS`) + `cosign verify` against the documented identity before running (v3.4 item 3, v3.5 item 4)** — unlike the JVM template, which builds from source, the v1 template consumes a signed release artifact. **The GitHub Action itself ships post-v1 in M7e (v3.3 C1)** — v1 is the template, not the action.

## 9. Testing and quality gates

- **Unit and property tests** (`bun test`): purl parsing, SBOM readers, OSV matcher (property tests against the `semver` package, **including the verified real-world shapes: multi-package `affected[]`, `last_affected`-only entries, `-npm` version suffixes, alias-file dedup with canonical-id selection, GIT-range-with-versions**), checksum parity with the shell script (at 230k files, property-tested for order independence), resolver (a fixture matrix of conditional `exports`/`imports` **including condition ordering and nesting**, package self-references, `#` imports, `require` vs ESM, `.mjs`/`.cjs`/`.mts`/`.cts` and the `type` field, `main`, nested duplicates, symlinked pnpm layouts, `npm:` aliases — pinned against the actual resolution behavior of the supported Node versions (v3.3, P0.5), **including the v3.4 alias pair (item 1): a `tsconfig` alias with a detected runtime mechanism must produce an edge marked `resolution: "tsconfig-alias"` (Next/Nest fixture), and one without a mechanism must produce no edge**. IR extraction per syntax form. **Parser fast-path differential test (v3.3, P1.4):** the TS-API and the acorn fast path must produce identical IR on the supported syntax subset (optional chaining, class fields, decorators, JSX, error recovery); the fast path is enabled only where equivalence is demonstrated, otherwise the TS parser is the fallback. **Adversarial matcher cases (v3.3, P0.3):** partially overlapping alias sets (no merge), conflicting ranges across records (kept separate), conflicting package identities (no merge), an advisory lacking any package identity (matches nothing), multiple `CVE-*` aliases (deterministic canonical choice).
- **Call-graph micro-benchmarks:** a labelled corpus of small snippets with expected edges per feature (closures, callbacks, prototypes, `bind/call/apply`, `EventEmitter`, re-exports, CJS/ESM interop, async/generators, dynamic require). Each snippet records expected *present* edges (soundness) and expected *absent* edges (precision). The corpus also covers the **real-world alias and dispatch forms of the soundness contract (v3.3, P0.1)** — `const f = obj[methodName]; f()`, destructured imports `const { handler } = require("pkg")`, `exports`/`module.exports`/prototype aliases, **re-assignment of a function after its definition**, callbacks registered through unmodeled wrappers, dependency-injection containers, `Proxy` (unsupported — recorded, marker expected) — with positive and negative cases per supported framework. **Gate (hard):** corpus passes in full.
- **Dynamic-edge oracle (v2, refined v3.1/v3.2):** run real test suites of several open-source apps under a **tracing harness — not coverage: V8 coverage records statement hits, not call edges — (CPU-profile call trees or explicit instrumentation, collected under a pinned Node runtime)**, collect observed caller→callee edges, and assert the static graph contains them. **Tracked as a per-release metric with a ratcheting floor (v3.2):** an **absolute minimum — proposed 80% of observed edges — is ratified in M0 *before* the first measurement** (M0 builds the harness and collects the traces; **the first floor measurement happens at M4, where the call graph exists**). The floor is **per-app with a ±1-point tolerance** (small noise or a changed app set must not fail a release), **ratchets upward only** (`floor(n+1) = max(floor(n), measurement(n))` per app), and the **primary metric is recall on package-boundary edges** (edges crossing from application or dependent-library code into library code) — trivial intra-app edges inflate the overall number, so overall recall is reported secondarily. **Fallback if the 80% minimum is unattainable at M4:** the floor is set at the measured value for one release, with the gap, the responsible dynamic features, and a remediation plan documented in the release notes; a permanent waiver requires an ADR (the minimum is a goal, the ratchet is the contract). This is the standard way to measure static call-graph unsoundness and the main defense against the "false negative" risk. **The 80% floor is an engineering acceptance gate, not evidence of safety (v3.3, P0.1):** a passing floor means the graph meets the ratcheted minimum; the release notes still state the supported subset and the known limitations per application, and **no release claims complete reachability** (release criterion, §5.5).
- **Golden demos** (`examples/`), npm, pnpm, Yarn (node-modules linker), and Bun layouts, in TS and JS, CJS and ESM:
  - *Positive:* an Express app pinning `lodash@4.17.20` and calling `_.template` → REACHABLE with trace. **(M0 must verify against the snapshot which canonical id reports — the record is stored under two GHSA ids with the CVE id absent; the demo's `expected-reachable.txt` lists the canonical id per §5.2.)**
  - *Multi-package record:* app installs `lodash` and `lodash-es`, one advisory, two candidates from one record (v2 fixture, §5.2).
  - *Mapped negative:* same package, app only uses `_.chunk` → artifact-level REACHABLE but mapped verdict UNREACHABLE.
  - *Installed-not-required:* package present in `node_modules`, never imported → UNREACHABLE with `installed: true`.
  - *Loaded-not-called:* package imported for side effects, vulnerable export never called → UNREACHABLE (default tier) with `evidence.loaded: true` (v2, §2).
  - *Fixed pin:* bump to the patched version → zero candidates, exit `0`.
  - *Dynamic risk:* `require(name)` with a computed name → NOTICE emitted.
  - *Import-time side effect (v3.3, P0.2):* `import "pkg"` executes the vulnerable code at load, no exported call → **mapping-level REACHABLE via `import → module-init → target`** while the artifact is UNREACHABLE at the default `call` tier with `installed: true` + NOTICE; a callback registered but never invoked is reported with `evidence.callbackRegistered: true` (registration ≠ invocation).
  - *Local patch / version drift (v3.3, P0.4):* an installed package patched in place without a version change → `RESOLVED` but the install fingerprint diverges from the lockfile → visible in `completeness`, `--strict-sources` exits 3; SBOM version ≠ installed version → `VERSION_MISMATCH` state, **advisory ranges matched against the installed version (v3.4 item 7)**, candidate analyzed against the installed code with a NOTICE and both versions on the finding.
  - *Partial resolution (v3.3, P0.8):* 99/100 components resolved, the missing one has no advisory → exit 0 with `analysisStatus: PARTIAL` (visible in console and all formats); the same missing component with an advisory → `NO_SOURCE` finding, still exit 0 by default, `PARTIAL`.
  - *Native boundary (v3.3, P0.6):* the app calls a native addon implicated by an advisory → `NATIVE_OPAQUE` with `nativeBoundary: "reached"`; `--opaque-native=fail` exits 1, the default `warn` exits 0; a boundary the app never reaches → `nativeBoundary: "unresolved"`, never a failure.
  - *`--sbom-only` (v3.3, P1.3):* an advisory is matched but no graph is built → no `REACHABLE`/`UNREACHABLE` verdicts in the report, `analysisStatus: "NOT_PERFORMED"`, **every component `resolutionState: NOT_CHECKED` (v3.4 item 9)**, and the SARIF/JUnit outputs do not present the run as a reachability check; default exits 0 (reported, not gated), `--fail-on-applicable` exits 1.

  - *Entry point in `dist/` (v3.5, item 5):* a Nest app runs its build output (`main` → `dist/main.js`) → the `dist/` files auto-join the input-key source hash with a warning; editing them invalidates the cached result.

## 11. Risk register

| # | Risk | Mitigation |
| --- | --- | --- |
| R1 | **Static call graphs for JS are unsound** (dynamic features); a green run may hide a real path. | Dynamic-risk markers and NOTICEs, `installed: true` on UNREACHABLE, dynamic-edge oracle with a ratcheting per-release floor (absolute minimum + upward ratchet, §9), `exposure {dynamicRisk, noSource, nativeOpaque, dynamicUnscoped, loadedNotCalled}` summary (+ `completeness.unlistedInstalled`, v3.5 item 1), `--over-approximate-dynamic`, conservative library models, documented limitations section. |
| R2 | **Engine cost.** Building the call-graph engine is far larger than wiring SootUp. | M0 spike, strict IR boundary, Jelly as oracle **and as a BSD-3 design reference for library models**, scope cut line: ship default + `--cha` in v1, pointer analysis later, **and M0 fixes the v1 entry-point scope per framework (§5.5 names ~15 frameworks across its five groups; M0 decides which ship in v1)**. |
| R3 | **Artifact-level verdicts are noisy**: importing `lodash` makes most of the package "loaded". | `CALLED` default tier, mapping files with public-export keys, curated mapping seed for top advisories, confidence + `matchLevel` levels. |
| R4 | **npm OSV snapshot size/performance.** | **Measured: 208 MB / 230,324 records** (32× the Maven set). Package-name + alias index cached by snapshot sha256; lazy record parsing; parallel pin/checksum computation. |
| R5 | **Bun compile surprises**: autoload of cwd config, worker bundling, native addons, flag churn between releases. | **Most flags measured on 1.4.2 (§7): autoload flags exist and default ON (fixed), worker rule pinned, 7+baseline targets cross-compile.** Remaining unknowns are flag churn across releases: pin Bun, hostile-cwd test, compiled-binary-only CI jobs, no-native-addon check, upgrade via Renovate PRs gated on the full e2e. |
| R6 | **Binary size and startup worse than the JVM native image.** | **Measured: ~81 MB floor, ~4 ms startup** — size is ~2.3× the JVM 35.8 MB image (a known, documented cost); startup is a non-issue. Per-platform npm packaging means each user downloads one binary; `--bytecode` verified to shrink nothing. |
| R7 | **Package-manager layout diversity** (pnpm symlinks, PnP, workspaces, aliases like `npm:foo@1`). | Layout adapters with a fixture per manager; explicit refusal over best-effort for PnP in v1; purl-to-directory verified by `package.json` name/version, not by path; app-vs-library by realpath; alias fixture in M2. |
| R8 | **Branch coverage unavailable under Bun.** | Runtime-agnostic core plus nightly Node/c8 gate. |
| R9 | **Large MAL-* surface and malware policy debates.** | Explicit `--malware` flag, **documented default `fail`**, separate verdict so reachability semantics stay clean; install-script NOTICEs are informational only. |
| R10 | **Analyzing untrusted repos**: the tool parses attacker-controlled files. | No code execution (parse-only, no `require` of target code), **cwd config autoloading disabled at compile time (measured flags, §7) + hostile-cwd test**, hostile-input fuzz corpus for the parser wrapper and JSON readers, **the v3.3 hardening list (§7): per-file/total byte caps, node/edge caps, worker timeouts + cancellation, archive path-traversal validation, JSON nesting bounds, limit-hit vs OOM-kill diagnostics**, signed releases. |
| R11 (new) | **OSV bucket naming/aliasing drift**: records move between database ids over time; an index or golden demo built on today's file names may miss a record renamed upstream. | Index keys on `aliases` (not file names only); canonical-id rule in §5.2; M0 verifies every demo advisory id against the fresh snapshot; the demo's expected list is regenerated by a script, never hand-edited. |
| R12 (new, v3.3) | **SBOM/lockfile/install drift**: the three describe different trees (in-place patches, version disagreement, duplicate instances) while the run exits 0 with apparently normal verdicts. | Per-component resolution states `RESOLVED/MISSING/VERSION_MISMATCH/AMBIGUOUS` (+ `NOT_CHECKED` in `--sbom-only`) in every report; `--strict-sources` covers all non-`RESOLVED`; the deterministic install fingerprint joins the cache keys; loaded-file content hashes (IR keys) catch in-place patches of loaded packages; **reverse reconciliation (v3.5 item 1): graph-loaded instances with no SBOM component → `unlistedInstalled` + `PARTIAL` + NOTICE, `--match-installed` extends candidate generation; `matchedOn` labels which version a mismatched finding matched on (v3.5 item 8)**. |
| R13 (new, v3.3) | **Stale caches**: a report or call-graph cache survives source/lockfile/model/mapping/tool changes. | Cache keys (per-file IR / input / memo — the v3.4 split) + install fingerprint (§6); the cache read/write consumes the same canonical definition; M8 invalidation matrix (including auto-included source directories, v3.5 item 5). |
| R14 (new, v3.5) | **SBOM staleness**: the SBOM describes a different tree than the installation (stale lockfile, different mount) — an installed, loaded package the SBOM never listed escapes the check while the run exits 0 with status `COMPLETE`. | Reverse reconciliation (§5.3, v3.5 item 1): `completeness.unlistedInstalled` + `PARTIAL` + NOTICE by default; `--match-installed` extends candidate generation to installed instances; the golden demo (SBOM omits a vulnerable transitive the app loads) pins it. |

## 12. Decisions — resolved (v3.5)

All five v1 questions are answered, and the four new ones surfaced during review are decided — all nine are settled (see the v3/v3.1/v3.3/v3.4/v3.5 change logs above).

1. **Primary target audience: application repositories** (Express/Nest/Next/Lambda/serverless), same posture as the JVM tool. M4 entry-point priority: server frameworks → serverless → async consumers → CLI mains. (Libraries use the tool in their own CI; no separate "library mode".)
2. **Binary size budget: ~90 MB per platform — user-accepted (v3)** (measured floor 81 MB; `--bytecode` changes nothing; startup ~4 ms so cold start is not a cost). Options (b) plain-JS distro and (c) downloader-shim remain available for a later release, not v1.
3. **Default policies:** `MALICIOUS_PACKAGE` ⇒ **fail (exit 1)** by default, `--malware=warn|ignore` to relax (the finding is never suppressed). `NATIVE_OPAQUE` ⇒ **reported with `opaque: true`, never a failure by itself** — **v3.3: `--opaque-native=fail|warn|ignore` (default `warn`); `fail` fails closed when an advisory-covered native boundary is *reached* (§5.6).**
4. **Yarn PnP: refused in v1** (exit 2 + hint), stretch item in M7c.
5. **Flag names: kept exactly from the JVM tool** where they carry over; `--project` replaces `--app-classes`+`--classpath-file`; `--java-version` dropped; JS flags are additive.
6. **(New) License: MIT — user-confirmed (v3)**; declared at the **M0 bootstrap** (v3.1 — every npm package needs the field from its first commit). (npm publish requirement; the JVM repo has none.)
7. **(New) Brand: `callis` — user-confirmed (v3)**: binary `callis`, npm scope `@callis/*`, report `tool.name` "callis" (§3.8). **Project: `callis-js`** — the repository keeps its current name, so no rename is needed.
8. **(New, v3.3; expanded v3.4 item 3) v1 distribution scope (C1–C3):** the **signed, downloadable release binary (assets + SHA256SUMS + cosign + provenance)** + the **multi-arch Docker image** + `callis-check.yml` + the Jenkinsfile. The npm packages, the GitHub Action, the macOS/Windows signatures, and the Turborepo/Nx cache integration all ship post-v1 in M7 — no npm install experience is promised before the package layout exists. **(v3.5 item 4: the supported v1 platform is Linux — glibc/musl, x64/arm64 + baseline; the macOS/Windows binaries ship as experimental and unsigned until M7d signs them; the template verifies via a repo-pinned digest + cosign identity, never the release's own checksums.)**
9. **(New, v3.3) Report schema versioning:** `schemaVersion` in every report, independent of `toolVersion`; field classes (mandatory / optional / extensible) documented; SARIF pinned to 2.1.0; unknown verdicts and properties forward-compatible.
